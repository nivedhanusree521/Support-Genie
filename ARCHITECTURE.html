1 High-Level Architecture

A user message enters a LangGraph loop where an LLM decides whether it needs a tool, a tool node runs exactly the tool(s) requested against local JSON/SQLite data, and the loop repeats until the LLM is ready to produce a final, grounded answer — with the whole conversation persisted so context carries across turns.

2 Full Request Lifecycle — Example

Walking through "My VPN is not working, please raise a ticket" end to end:

  1. User → UI: message typed into the Streamlit chat input.
  2. UI → Graph: graph.invoke({"messages":[HumanMessage(...)]}, {"configurable":{"thread_id": ...}}).
  3. Graph → LLM: system prompt + full message history sent to gpt-4o-mini with the 4 tools bound.
  4. LLM decides: if employee_id/description are incomplete, it responds with a clarifying question and no tool call → routed straight to END (note: the LLM classifies the category itself from the description — it never asks the user for it).
  5. Once complete: LLM emits a create_ticket tool call → routed to the tools node.
  6. Tool executes: validates the employee exists, checks for a duplicate open ticket, inserts a new row into SQLite, returns a structured JSON result.
  7. Loop back: the tool's ToolMessage is appended to state and control returns to the agent node.
  8. Final answer: the LLM reads the tool result and phrases a natural-language confirmation — never raw JSON.
  9. UI renders: the answer plus a "🔧 Tool activity" panel showing exactly what was called and what it returned.
✅ This is exactly what "State → Routing → Multi-Step Workflow" means in practice: the agent can branch (ask vs. act), loop (tool → agent), and remember (checkpointed state) — not just answer in one shot.

🆕 New-Employee Onboarding Flow

The seeded employees.json is a starting directory, not a hard limit. A fourth tool, register_employee, lets the agent create a real row in SQLite on demand:

  1. User: "I'm a new employee, I don't have an ID."
  2. Agent (no tool call): asks only for first name, last name, and department/role — never email or employee ID.
  3. User: "Vikram Rao, Operations."
  4. Agent → register_employee: always succeeds — it counts existing employees whose email already matches vikram_rao(\d*)@xyz.com; here that's 0, so the email is vikram_rao@xyz.com (a 2nd "Vikram Rao" would get vikram_rao1@xyz.com, a 3rd vikram_rao2@xyz.com, and so on) — then inserts a new row with a server-generated EMP#### ID. Neither value is ever invented by the LLM, and a shared name never blocks registration.
  5. Agent: "You're registered as EMP7421. How can I help?"
  6. User: "My laptop won't turn on, please raise a ticket."
  7. Agent → create_ticket: uses EMP7421 automatically — no need to re-ask, because the conversation state (persisted via SqliteSaver) already carries it.
🔒 Key safety property: employee IDs and ticket IDs are always generated inside db.py, never by the LLM — so the model cannot guess, invent, or duplicate an ID, and every registration lands as a real, queryable row in it_support.db.
👥 Business rule: names can repeat, registrations never block. Any number of employees may share an identical first and last name — register_employee always creates a new record rather than refusing or asking the agent to "resolve" a clash. Uniqueness lives entirely on the email, disambiguated with an incrementing suffix: 1st "Jane Doe" → jane_doe@xyz.com, 2nd → jane_doe1@xyz.com, 3rd → jane_doe2@xyz.com. Each still gets its own independent EMP#### ID.

3 Component-by-Component Breakdown

🖥️ Presentation Layer app.py

Renders the chat UI plus a persistent multi-chat sidebar backed by SQLite: every chat has its own chat_id (row in the chats table — title + rendered history) and thread_id (key into the LangGraph checkpointer). Invokes the graph on every message, unpacks the returned messages to show a transparent "Tool activity" trace, and saves the updated history back to chats. A 🗑️ button next to each chat permanently deletes both its row and its LangGraph state. Wraps everything in try/except so failures degrade to a friendly error instead of a crash.

Why Streamlit: the brief recommends it explicitly, and it delivers chat + history + reset + result-visibility with minimal code, keeping focus on the agent logic.

⚙️ Configuration Layer src/config.py

Loads OPENAI_API_KEY, OPENAI_MODEL, LLM_TEMPERATURE, and EMAIL_DOMAIN (used to auto-generate new employee emails) from .env via python-dotenv, and centralizes every file path (data dir, DB path, JSON seed files). No other file hard-codes a secret, domain, or path — everything is portable and testable from one source of truth.

🗄️ Persistence Layer src/db.py

Defines employees, tickets, and chats tables, auto-seeds employees/tickets from JSON on first run (idempotent), and exposes focused helpers: get_employee, generate_unique_employee_email, create_employee, find_tickets, find_open_ticket_for_duplicate_check, create_ticket, plus create_chat / list_chats / get_chat / update_chat / delete_chat for the sidebar's persistent chat list. Generates unique TCK-XXXX ticket IDs and EMP#### employee IDs server-side, each with collision checking — the LLM never supplies these values itself. generate_unique_employee_email counts existing employees whose email matches the requested name pattern and appends the next number, so repeated names never collide.

Why SQLite: tickets and employees are relational — a real, embedded, zero-config database expresses filtering/inserts more honestly than hand-rolled JSON manipulation, and demonstrates genuine local database integration.

📚 Reference Data data/knowledge_base.json

A flat JSON array of IT articles tagged with keywords for matching. Static and read-only, so plain JSON is the right level of complexity — it also contrasts cleanly with the writable, relational ticket data in SQLite.

🛠️ Agent Tools src/tools.py

Four @tool-decorated functions, each with a Pydantic input schema and a docstring that doubles as the LLM's usage instructions.

ToolSchemaGuardrail
knowledge_searchqueryReturns found: false rather than fabricating an answer
ticket_lookupemployee_id?, ticket_id?, keyword?Requires at least one search criterion
create_ticketemployee_id, category, descriptionRejects unknown employees; flags duplicates instead of auto-creating; category is self-classified by the LLM from the description, never asked of the user, and normalized to a fixed allow-list
register_employeefirst_name, last_name, departmentEmail auto-generated as firstname_lastname@xyz.com (incrementing a suffix if the name repeats) — never asked of the user; always creates a new record, never blocks on a shared name; ID always server-generated

Every tool wraps its logic in try/except, returning a structured error dict instead of raising — the graph never crashes on a bad call.

🆕 register_employee is what makes the system open-ended: any user can identify as new, supply just their first name, last name and department, and be inserted into the real database — the email and employee ID are always generated by the system, never typed or invented, and a name that's already in use just gets the next numeric email suffix rather than being rejected — after which they can look up or create tickets exactly like a pre-seeded employee.
🧩 Conversation State src/state.py 
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    employee_id: Optional[str]

add_messages is LangGraph's reducer that automatically appends each node's new messages to the running history — the backbone of both tool-calling and multi-turn memory.

🧠 Orchestration Layer src/graph.py

The heart of the system. Wires an agent node (LLM + bound tools), a tools node (ToolNode), a conditional edge (tools_condition) that routes to tools only when a tool call is present, a loop-back edge so the agent phrases the final answer after seeing tool output, and a SqliteSaver checkpointer keyed by thread_id for persistent state.

The system prompt encodes every safety rule from the brief: never invent information, collect all required fields before creating a ticket or registering a new employee, self-classify the ticket category from the description instead of asking the user, ask only for first name/last name/department when registering (never email or employee ID — both are system-generated), offer to register the user when their employee ID isn't found instead of giving up, surface duplicate warnings, and report tool errors plainly.

📋 Observability src/logging_config.py

A single shared logger used by every module — DB seeding, tool calls with their arguments, ticket creation, exceptions — giving a clear audit trail of every decision the agent made, without extra dependencies.

✅ Verification tests/test_tools.py

LLM-independent smoke tests covering the happy path, "not found", unknown-employee rejection, duplicate-ticket detection, successful registration (immediately followed by creating a ticket under the new ID), duplicate-email detection, and missing-field rejection — 11 tests across all four tools, proving correctness in isolation before the non-deterministic LLM ever gets involved.

4 Project Structure

Every file has exactly one job. Nothing is duplicated, nothing is hard-coded across files, and the layout separates presentation (app.py), orchestration (graph.py, state.py), capabilities (tools.py), persistence (db.py, data/) and configuration/observability (config.py, logging_config.py) into clean, independent layers.

🧱 Why this layering matters: each layer can be understood, tested, and modified independently — e.g. swapping SQLite for Postgres would only touch db.py; swapping OpenAI for a local model would only touch graph.py; none of it would require changing tools.py or app.py at all. This is exactly the "clean, modular and understandable code" the assignment calls for.

6 Data Flow Summary

🌱

Seeding (once)

employees.json + seed_tickets.json → auto-inserted into it_support.db on first init_db() call.

🔎

Read path

knowledge_search reads JSON directly; ticket_lookup runs a parameterized SQL SELECT.

✍️

Write path

create_ticket validates, checks duplicates, then INSERTs a new row — the only write path in the system.

Every tool returns a structured dict → wrapped as a ToolMessage → fed back to the agent node → rendered as a grounded natural-language answer in the Streamlit UI.

7 Why This Design Fits the Brief

🎯 "Tool Calling → Agent → State → Routing → Multi-Step Workflow" maps directly onto this system: Pydantic tool schemas (Tool Calling), the agent node (Agent), AgentState + SqliteSaver (State), tools_condition (Routing), and the agent ⇄ tools loop (Multi-Step Workflow).
🔒 Safety first — the agent is architecturally prevented from creating a ticket with missing or invented information, and is nudged rather than forced to confirm before a likely duplicate.
👁️ Transparent by design — every tool call and its raw result is visible in the UI's tool activity panel and in the logs, never hidden inside a single LLM response.
🌱 Open-ended, not a fixed demo dataset — the register_employee tool means the system isn't limited to the 6 seeded employees; anyone can onboard themselves through the chat and drive the full ticket lifecycle under their own identity.
💾 Genuinely persistent, not just "for the demo" — both conversation memory (SqliteSaver → checkpoints.db) and the chat list itself (chats table → it_support.db) are backed by real SQLite files, so closing and restarting the app preserves every saved chat exactly as Streamlit apps in production would need to.
